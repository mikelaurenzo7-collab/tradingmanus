# Kalshi API repository review notes

- The GitHub `kalshi-api` topic page surfaces a broader set of resources than the single `quantgalore/kalshi-trading` repository, including a high-star autonomous bot, the `pykalshi` unofficial Python client, Rust SDKs, data collectors, and multi-market prediction-market frameworks.
- The most promising categories for this project are client libraries and data/market-structure tools rather than strategy repos with narrow market assumptions.
- The current review priority is to inspect repositories that may improve market data normalization, execution reliability, and candidate selection for standard Kalshi markets.

The `pykalshi` repository appears materially useful as a **reference implementation for production-grade client behavior**. Its most relevant patterns for this project are WebSocket streaming, automatic retries and backoff, typed domain models for markets and orders, local orderbook state management from deltas, and explicit portfolio/order workflows. It also highlights concrete production concerns we should keep tightening in this app: bounded error handling, rate-limit resilience, better orderbook-driven market qualification, and cleaner separation between market browsing, signal generation, and order execution.

The `quantgalore/kalshi-trading` repository points in a different but equally important direction. Its README frames the task as choosing **the most optimal contract** inside a narrow market family, and the production script visibly builds a feature-driven model from underlying-market intraday data, session timing, and volatility context before selecting a Kalshi bracket. The practical takeaway for LAURENZO is that trustworthy autonomous candidates should come from **domain-specific probability estimation** and **narrow market families**, not from applying a neutral `50%` fair-value fallback across arbitrary sports props. That supports tightening the current pipeline so fallback-derived value plays are treated as heuristic-only or excluded from autonomous execution unless an independent probability estimate exists.

The `kalshi-live-production.py` source confirms that the strategy is **forecast-first and contract-second**. It predicts an expected SPX move range from historical intraday volatility features, pulls the same-day Kalshi event, parses each contract's strike band, and then ranks contracts by the smallest distance to the predicted bounds. The broader lesson for Laurenzo is that autonomous eligibility should continue to prefer markets anchored to an explicit underlying forecast or event-specific probability model rather than a broad neutral-baseline mispricing scan.
